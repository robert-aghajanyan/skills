# Lockfiles

Use this file to check manifest and lockfile consistency without turning the review into a broad upgrade project.

## Expected Pairings

| Manifest | Expected lockfile | Notes |
| --- | --- | --- |
| `package.json` with npm | `package-lock.json` or `npm-shrinkwrap.json` | CI should prefer `npm ci`. |
| `package.json` with Yarn | `yarn.lock` | Yarn 2+ should usually use immutable installs. |
| `package.json` with pnpm | `pnpm-lock.yaml` | Workspaces should include `pnpm-workspace.yaml` when applicable. |
| `package.json` with Bun | `bun.lock` or `bun.lockb` | Confirm the repo's Bun version if lockfile format changed. |
| `pyproject.toml` with Poetry | `poetry.lock` | Lockfile should be regenerated by Poetry, not hand edited. |
| `pyproject.toml` with uv | `uv.lock` | `uv sync --frozen` is the common consistency check. |
| `Pipfile` | `Pipfile.lock` | Confirm both default and develop packages. |
| `requirements*.txt` | optional compiled lock or hash-pinned file | Check whether files are inputs or generated outputs. |
| `Cargo.toml` | `Cargo.lock` | Applications should generally commit it; libraries may intentionally omit it. |
| `go.mod` | `go.sum` | Missing or stale sums are a consistency concern. |
| `composer.json` | `composer.lock` | Applications should usually commit it. |
| `Gemfile` | `Gemfile.lock` | Lock should reflect the intended platforms. |
| `.csproj` or `packages.config` | `packages.lock.json` if locked restore is used | Check `RestorePackagesWithLockFile`. |

## Drift Checks

- Compare changed manifests and changed lockfiles. A manifest changed without a lockfile update is suspicious when the ecosystem expects a lock.
- Compare lockfile mtimes and git diffs only as hints. The authoritative check is a repo-native frozen install or lock check.
- Flag multiple lockfiles for one package manager family when CI does not clearly select one.
- Check lockfile package source fields. A version can remain unchanged while source, registry, tarball URL, or integrity hash changes.
- Confirm integrity fields where the ecosystem supports them, such as npm `integrity`, pnpm integrity data, Cargo checksums, Go sums, and Composer dist hashes.
- Treat checked-in dependency directories (`node_modules`, `.venv`, `vendor/bundle`, `target`, generated package caches) as generated dependency artifacts unless the repo explicitly vendors them.

## Validation Examples

Use repo-native commands from docs or CI first. Many commands may touch caches or need network access; ask before running networked checks.

```bash
npm ci --ignore-scripts
yarn install --immutable --ignore-scripts
pnpm install --frozen-lockfile --ignore-scripts
bun install --frozen-lockfile
uv sync --frozen
poetry lock --check
pipenv verify
cargo generate-lockfile --locked
go mod verify
composer validate --strict
bundle check
dotnet restore --locked-mode
```

## Reporting Guidance

- If you cannot run a frozen install, report the exact local evidence and list the frozen install as the validation command.
- Do not ask for lockfile regeneration unless the manifest/lock mismatch is clear.
- If a repo intentionally does not commit a lockfile, evaluate whether it is a library, application, deployed service, or reusable template before calling it a risk.
